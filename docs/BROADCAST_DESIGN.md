# 广播系统设计文档

版本：v1.0（2026-10-10）
状态：设计阶段，未实现

## 一、广播的定位

广播不是"消息推送"，是"事件分发系统"。

它涉及十个维度：一致性、持久性、顺序、安全、审计、优先级、离线、加密、组播、回执。

SASES 当前只做了最基础的一层（同进程 WS 广播）。

## 二、广播的三层分级

### L1：进程内广播（已实现）

场景：单节点多窗口、单设备多账号
- WS 连接池内所有客户端
- 无网络开销
- 现有实现：ws_routes.broadcast_to_user / broadcast_to_group

### L2：节点间广播（待实现）

场景：主节点 → 副本、跨服务器
- 8001 ↔ 8002 ↔ 8003
- 需要"节点间通道"
- 上服务器时新增

### L3：用户级广播（待实现）

场景：用户手机 ↔ 电脑
- 通过 L2 中继 + 用户级寻址
- 蜂巢终局

## 三、跨节点广播的实现方案

### 方案 A：HTTP 轮询

副本每 2 秒问主节点"有新消息吗"
- 简单
- 延迟 2 秒

### 方案 B：WS 长连接（推荐）

副本主动连主节点的 `/ws/hive/broadcast`
- 实时
- 需要重连机制

### 方案 C：消息队列

引入 Redis/RabbitMQ 做中转
- 生产级
- 需额外服务

## 四、多账号 + 节点 + 广播的关系

### 蜂巢层（底层协议）

物理设备 = 1 个节点
- 节点 ID = 设备的 Ed25519 公钥
- 节点持有：1 个或多个账号的密钥

### 智维空间（用户界面）

显示时按"账号"展开
- 账号 X 的节点
- 账号 Y 的节点
- 但底层指向同一个蜂巢节点

### 广播路由

- 账号级广播（L1）：同节点内直接
- 节点级广播（L2）：跨节点
- 用户级广播（L3）：跨设备

**关键：广播按"账号"寻址，路由按"节点"分发——两个维度正交，不冲突。**


## 五、十个维度详解

### 维度 1：持久性

**问题**：广播纯内存，节点掉了消息丢。

**分类**：
- 瞬时广播（光标、正在输入）：不落库
- 持久广播（消息、转账）：落库 + 拉取补偿

### 维度 2：顺序

**问题**：不同节点收到顺序可能不同。

**分级**：
- 单聊：不需要（只有两人）
- 群聊：需要（按服务端时间戳）
- 积分转账：必须

**已有基础**：logical_clock 字段（B0 预留）

### 维度 3：幂等

**问题**：同一条广播收到两次。

**方案**：
- 广播带 message_id（已有 global_msg_id）
- 客户端 _seenIds Set 去重
- 服务端给广播加去重表

### 维度 4：广播风暴

**问题**：1000 节点，每个广播 1 次/秒 = 999,000 次/秒。

**方案**：
- 分层广播（小中枢→大中枢）
- Gossip 协议（随机 3-5 邻居）
- Pub/Sub 消息队列

蜂巢 3 层架构天然适合分层广播。

### 维度 5：实时性配置

**用户级配置**：
- realtime（立即推送）
- batched（5 分钟批量）
- silent（静默，打开时拉取）

当前：所有用户都是 realtime。


### 维度 6：安全（防伪造）

**问题**：攻击者伪造广播"用户 A 转账 1000"。

**方案**：
- 广播带发送节点 Ed25519 签名
- 接收方验签
- 用户级广播还要带 JWT

**已有基础**：identity.py + B1.2-B 的转发验签。

### 维度 7：回放攻击

**问题**：录制旧广播重放。

**方案**：
- 广播带 timestamp + nonce
- 接收方记录最近 nonce（滑动窗口）
- 超过 5 分钟的广播拒绝

### 维度 8：广播范围

**标签**：
- all_nodes（全网）
- my_devices（我的设备）
- my_friends（好友）
- specific_nodes（指定）

当前：只有 broadcast_to_user。

### 维度 9：广播日志（审计）

**问题**：用户投诉"消息没到"，无法查证。

**方案**：
- broadcast_log 表
- 记录：广播 ID、发送节点、接收列表、成功数、时间
- 保留 7 天

### 维度 10：兼容性

**问题**：新旧版本广播格式不同。

**方案**：
- 广播带 version 字段
- 接收方按版本处理
- 不认识的字段忽略

## 六、三种一致性模型

| 操作 | 一致性 | 策略 |
|------|-------|------|
| 聊天消息 | 最终一致 | 异步广播，2 秒延迟可接受 |
| 积分转账 | 强一致 | 同步确认 |
| 宠物喂养 | 最终一致 | 本地先写，后台同步 |
| 群成员变更 | 强一致 | 所有节点立即一致 |

**建议**：加 consistency_level 标记。

## 七、读扩散 vs 写扩散

| 模型 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 写扩散 | 给每个接收者写一份 | 读快 | 写爆炸 |
| 读扩散 | 只写一份，接收者来读 | 写快 | 读慢 |

SASES 现状：群聊写扩散，单聊读扩散。

**建议**：明确每种场景的模型，不要混。

## 八、离线消息队列

**问题**：用户离线时，广播消息丢失。

**方案**：
- 服务端每用户 offline_queue 表
- 广播时若用户离线 → 进队列
- 用户上线 → 拉取 + 标记已投递

已有基础：messages 表记录了所有消息。缺"已投递标记"。


## 九、补充维度

### 撤回与编辑

- 物理删除（对方也删）
- 逻辑删除（微信做法，显示"已撤回"）
- 不广播（只删自己）

**推荐**：逻辑删除。

### 已读回执

"已读"状态也是广播，覆盖用户所有设备。

**广播分类**：
- 事件广播（新消息、转账）
- 状态广播（已读、正在输入、在线）

### 重试和超时

- 广播带 ack_required 标记
- 重要广播 → 等 ack，超时重试
- 普通广播 → fire-and-forget

### 优先级队列

- P0：系统通知、紧急告警 → 秒级
- P1：用户消息、转账 → 亚秒级
- P2：状态同步 → 秒级
- P3：日志、心跳 → 分钟级

### 广播组

broadcast_to_group(group_id, msg) —— 广播给一组用户。

### 送达率统计

- 记录 delivery_targets
- 每个接收者回 ack
- /hive/broadcast/stats 显示送达率

### 端到端加密

E2EE 下节点只能转发密文，不能解密。
代价：无法搜索、无法审核、群密钥复杂。

## 十、三个根本问题

### 问题 1：广播是事件流还是状态同步

- 事件流：保留所有事件
- 状态同步：只保留最新状态

SASES 现在混用了。建议明确每个 API 的语义。

### 问题 2：广播是谁的责任

- 发送方：只负责"我发了"
- 主节点：负责"全网都能收到"
- 接收方：只负责"我收到了"

当前主节点是广播中心，主节点挂了广播停摆。
建议：广播责任下沉，主节点只做"排序和去重"。

### 问题 3：是否需要全局唯一顺序

- 聊天消息：不需要（时间戳）
- 积分转账：需要（防双花）
- 群主变更：需要

建议：分级处理，不追求"所有事都全局有序"。

## 十一、优先级

| 优先级 | 项 | 工时 |
|--------|----|------|
| P0 | 强一致 vs 最终一致区分 | 半天 |
| P0 | 离线消息队列 | 半天 |
| P1 | 广播带签名 | 半天 |
| P1 | 已读回执广播 | 半天 |
| P2 | 撤回/编辑 | 1 天 |
| P2 | 优先级队列 | 半天 |
| P3 | 广播组 | 半天 |
| P3 | 送达率统计 | 半天 |
| P4 | E2EE 兼容 | 1 周 |

## 十二、分阶段实施

### 阶段 1（现在不做，上服务器前）

- L2 节点间广播通道
- 广播带签名
- 广播日志表

### 阶段 2（多用户协作时）

- 离线消息队列
- 优先级队列
- 已读回执

### 阶段 3（蜂巢终局）

- L3 用户级广播
- Gossip 协议
- E2EE

## 十三、与现有系统的关系

- 与 B1.2-B 转发：转发是"请求-响应"，广播是"事件分发"，两者互补
- 与 node_registry：广播需要知道节点列表
- 与 identity.py：广播需要签名

## 十四、一句话总结

广播是"事件分发系统"，涉及一致性、持久性、顺序、安全、审计、优先级、离线、加密、组播、回执十个维度。

SASES 当前只做了最基础的一层，随着场景增加，每个维度都需要补齐。

## 十五、决策建议

1. **不改当前实现**——现有 WS 广播能工作，测试阶段够用
2. **加字段预留**——logical_clock、message_id 已存在，无需额外
3. **等真实需求**——上服务器时做 L2，多用户协作时做离线队列
